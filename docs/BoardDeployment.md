# Build, flash and profile from the editor

Relaunch the standalone app and open **Help → Open STM32H7S78-DK Adventure**. The revised Willowlight riverside village has layered cottages, trees, street lamps, benches, crates, barrels, flowering planters, an animated fountain and shore water, a taller four-direction traveller and sword animation. Scenery has compact ground colliders and sorts at collider feet so that the player can walk behind overhangs. Ground tilemaps remain compressed; NeoChrom exports use aligned ARGB8888 textures, and source artwork stays editable.

The DK demo enables **Project settings → Touchscreen controls** by default. Hold or slide between arrows to move, lift and press **SWORD** or **TALK**. The reference driver reports a single pointer. [Customize or disable the overlay](TouchControls.md).

Click **Build & flash** in the toolbar, or **Project → Build & flash STM32H7S78-DK…**.

1. Select **NeoChrom hardware acceleration** and a 30 or 60 FPS refresh target. Click **Build firmware**. The app exports the current in-memory document into its own build workspace and invokes the bundled Python board builder; no terminal export or dev server is needed. The first build downloads the pinned LVGL/ST board SDK.
2. Connect the board through **CN7 / STLINK USB-C**, then click **Refresh probes**. Select its ST-LINK serial number. The app does not write a device until **Flash & run** is pressed.
3. **Replace bootloader** defaults off, preserving the installed bootloader during normal game updates. Enable it explicitly only when installing the matching boot image for this port. Flashing verifies the STM32H7R/S device ID, programs and verifies external application flash at `0x70000000`, optionally programs/verifies the boot image at `0x08000000`, and resets. Existing firmware at those addresses is replaced. The exact H7S78-DK external loader is selected from the installed CubeProgrammer directory. No mass erase, option-byte changes or readout-unprotect command is issued.
4. The board shows a diagnostic overlay, and the editor starts **Monitor FPS**. Use the touch arrows/SWORD/TALK while watching the FPS and GPU interrupt count. Bootloader replacement stays off for normal game updates and turns off again after an explicit successful installation.
5. To compare renderers, choose **Software comparison (GPU drawing off)**, rebuild and flash. Both modes retain the same LTDC/DMA2D display-flush path; the comparison disables NeoChrom drawing. Project or option edits mark the previous build stale and disable flashing until rebuilt.

**Tool settings** can override the CubeProgrammer CLI path and ARM GNU `bin` directory. Python 3, CMake, Ninja, Git and ARM GNU GCC/G++ with newlib must be installed. On macOS the builder can find the complete toolchain inside STM32CubeIDE. CubeProgrammer supplies the ST-LINK driver and `MX66UW1G45G_STM32H7S78-DK.stldr`. Tool executables are invoked directly with argument arrays. Compiler output and programmer diagnostics appear in **Build & device log**. Build cancellation terminates its process group; flash verification is allowed to finish before the app closes.

## What the measurements mean

The FPS value counts LVGL refreshes that actually rendered content. It is **not** the panel's physical scanout rate: a still scene can refresh at only the water/animation rate. Move through the world for a renderer comparison. Render time uses the Cortex-M7 DWT cycle counter. Flush/wait time sums LVGL's flush callback and flush-wait durations; it is CPU time spent submitting/waiting, not a direct measurement of LCD wire latency. The GPU value counts GPU2D interrupts, while the renderer flag reports whether NeoChrom drawing is enabled. A configured renderer alone is not evidence that every draw operation was accelerated; unsupported tasks can use software.

The adapter publishes a 48-byte versioned telemetry block in the port's uncached RAM_CMD section. The build report records its linked address. CubeProgrammer reads that block with **HOTPLUG** SWD access without halting/resetting the game, so no UART cable or serial driver is required. A sequence counter rejects torn samples. The editor identifies a sample that stops advancing as stale. Polling is about once per second and has some debug-bus overhead; for the cleanest timing comparison, compare the on-screen overlay with monitoring stopped.

The implementation follows [ST's CLI reference](https://dev.st.com/stm32cube-docs/prog/2.23.0/en/docs/markup/CubeProg_Command_Lines.html) and preserves the [official LVGL board port](https://github.com/lvgl/lv_port_stm32h7s78-dk). See [the board foundation and manual build guide](STM32H7S78-DK.md) for the pinned revisions, memory map and source integration. [Original art and generation prompts](../assets/willowlight/README.md) are retained with the project.

## Verification and device connection

Both M7 variants cross-compile and link against the real ST HAL and LVGL/NemaGFX library. A packaged-app test presses **Build firmware**, compiles the actual application, reaches Ready, checks probe-dependent flash disabling and verifies stale-build detection after changing renderer. Native LVGL 9.4/9.6 tests run the richer scene using a **300 KiB LVGL heap**. Automated flash tests use a simulated programmer to check device identity, serial selection, binary hashes, exact write/verify/reset order and concurrent-operation rejection; these do not program physical hardware.

The initial ST-LINK connection failed in both CubeProgrammer GUI and CLI. Connecting CN7 through a USB High-Speed hub resolved communication on this Mac. On 2026-10-19, CubeProgrammer 2.23.0 programmed the corrected NeoChrom application into external NOR, verified it and reset into the game. Independent readback matched the application, the final sector's remaining 35,336 bytes were preserved, and all 64 KiB of internal flash remained unchanged. Backups are retained in `.local-examples/device-flash/20261019-204848`.

Three initial live samples measured 10.891–13.307 rendered FPS, with advancing uptime, frame and GPU interrupt counters. A further sample after 107 seconds confirmed continued operation. These are rendered-content measurements, not a controlled movement benchmark. The user confirmed that the artwork and touch controls work on the physical board. See the [device report and raw CLI logs](../evidence/h7-cli-device-2026-10-19/report.json).

## CLI deployment and current USB connection finding

The deployment plan uses the exact `MX66UW1G45G_STM32H7S78-DK.stldr` installed with CubeProgrammer. Its StorageInfo declares 128 MiB of external NOR at 0x70000000, 256-byte pages and 64 KiB erase sectors. Before programming, the CLI workflow identifies the MCU, backs up all 64 KiB of internal flash and the complete affected external sectors, and confirms the external backup with a second read. The candidate is overlaid on those sector bytes so the tail beyond its end survives sector erasure. Programming verifies the merged image; independent external readback and unchanged internal flash are checked before reset. No boot image, mass erase, option-byte change or unprotect operation is requested.

The prepared application startup now replaces the vendor application's automatic `HAL_FLASHEx_OBProgram` path with a read-only compatibility check. Incompatible watchdog/XSPI/I2C configuration stops startup instead of changing option bytes. The Boot image remains unchanged and is preserved during normal application updates. Current build reports record `applicationOptionBytes: read-only compatibility check`.

A direct-port retry could identify the ST-LINK serial, firmware V3J15M6, STM32H7S78-DK and 3.27 V, then failed reading the core ID with USB errors 0xe00002ed/0xe000404f. Another direct Mac port and under-reset mode failed as well. This matches the failure pattern in [ST's STLINK-V3/computer USB interoperability FAQ](https://community.st.com/stm32-mcus-60/faq-possible-communication-failure-between-stlink-v3-and-some-recent-computers-141999). ST recommends another host port, an external USB High-Speed hub or another debug probe. The hub connection subsequently succeeded, including repeated flash reads, programming and verification; the underlying USB interoperability diagnosis remains an inference.
